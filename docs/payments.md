# Durable sandbox payments

P02 extends [foundation setup](foundation.md). Apply migrations through version 5 with `go run ./cmd/migrate`, build the frontend, and run both `cmd/api` and `cmd/worker`. Product config remains in an explicitly selected ignored `ENV_FILE`; never overwrite populated `.env`. Add paired `PAYPAL_CLIENT_ID` and `PAYPAL_CLIENT_SECRET`, the actual allowlisted `PAYPAL_MERCHANT_ID`, and the same app's `PAYPAL_WEBHOOK_ID`. Only `https://api-m.sandbox.paypal.com` is accepted. Without credentials, intake still works and checkout reports unavailable. The JavaScript SDK receives its public client ID; credentials, bearer tokens and verification calls stay server-side.

Checkout binds the senior's immutable request version, digest, amount, currency and actual merchant before any provider call. The button creates an AUTHORIZE order, and approval queues authorization only. A confirmed authorization produces HELD. An order's COMPLETED status is not proof of capture. The named relative does not receive the merchant payment.

Every command has a durable UUID/request hash and persisted payload before dispatch. Capture/void are mutually exclusive under a household/intent transaction and a partial unique index. Provider calls run after commit. Workers use 60-second fenced leases, bounded exponential retries and dead letters; a late worker cannot acknowledge a replaced lease. Household/intent locks precede job fences. Restart recovery reads provider truth before replay. Create/authorize replays use the original request ID within a conservative 10-minute troubleshooting bound; that bound is not a claimed PayPal retention guarantee. Cleanup retries reuse the same void command/request ID.

Capture recovery preserves the original operation, authorization, exact persisted payload and request ID. This product sends only the full authorized amount with `final_capture=true`, never partial capture or reauthorization. PayPal documents that a final capture closes additional captures on that authorization and rejects already captured authorizations. If GETs report CREATED/HELD with no capture, the worker rechecks current PG evidence, confirmation, membership, consent, totals, deadline and cancellation before replaying that same full/final command. This uses provider authorization finality in addition to idempotency; it does not invent an idempotency-cache retention duration. Known pending/completed/closed results and invalidated eligibility never trigger capture replay. An unresolved or contradictory result remains visible and can dead-letter; no new operation/key or forced terminal state clears it.

Held totals require a confirmed persisted authorization identity. Uncertain create/authorize work without an observed authorization remains unresolved exposure, not confirmed held money. Migration 005 advances household history revision when confirmed-held/captured totals change; transitions within the same held bucket preserve the current reservation's evidence.

Capture is unavailable in the ordinary P02 product. There is no public capture/review-approval route, bypass flag or development eligibility switch. `ReviewApprove` is a server seam for P03. It requires a current independently authenticated subject confirmation, reviewer membership/assignment, exact request/consent/history binding, approved classifier/encoder manifests and result, successful required lookup receipts (including legitimate empty results), revalidated private hits, current complete PG totals, explicit rationale and current evidence configuration. `payment_evidence_config` deliberately has no production seed. Eligibility is checked again before an undispatched capture runs. Private tests insert typed fixtures into isolated test schemas; they are not deployed integrations.

Senior cancellation and reviewer decline, deadlines, reconciliation and existing-hold cleanup do not call ML or Elastic. A capture already dispatched may complete despite a late cancellation. CAPTURE_PENDING, VOID_PENDING and RECONCILING never imply completion. Provider-confirmed VOIDED does not promise when a funding-source hold disappears. Bound versions cannot be edited; replacement requests use separate identities, while delayed approval on a cancelled old order is reconciled and any actual uncaptured hold is voided.

All product mutations retain the foundation's session/CSRF/Origin checks. Added routes:

| Route | Behavior |
|---|---|
| POST `/api/intents/{id}/paypal-order` | Senior; `expected_version`, `Idempotency-Key`; reserve immutable order |
| POST `/api/intents/{id}/authorize` | Senior; matching `order_id`, `expected_version`, key; authorize only |
| POST `/api/intents/{id}/cancel` | Owner/assigned reviewer; `expected_version`; cleanup request and current financial truth |
| GET `/api/intents/{id}/payment-diagnostics` | Scoped DB command/key/hash/lease/retry/dead-letter/overdue details; no secrets or raw bodies |
| GET `/api/intents/{id}/provider-state` | Scoped authoritative provider GETs only; no money command or state override |
| POST `/api/webhooks/paypal` | Signature-verified provider route; session/Origin exempt, 256 KiB limit |

Verified event IDs/raw bodies are stored transactionally before acknowledgement; raw bodies expire after 24 hours and have no product read route. Known events queue reconciliation in the same transaction; early unmapped events remain durable and are mapped by the worker. Events trigger provider reads rather than overwriting state. Completed capture truth cannot be reversed by late authorization events. Provider observations store only normalized IDs, merchant, exact money, statuses and debug IDs.

The official same-app event list is checked before registration by `go run ./cmd/paypal-webhooks -mode inspect`. Registration subscribes to authorization CREATED/VOIDED, capture COMPLETED/PENDING/DECLINED/REVERSED and checkout ORDER.APPROVED. The handler also recognizes the older v1 DENIED event, but the v2 registration uses DECLINED. Use `-mode register -url https://<listener>/api/webhooks/paypal`, save its returned ID in private config, and restart the API/worker. Real postback verification requires that actual ID; simulator events are not accepted or claimed as real proof.

For a temporary test listener, `cmd/webhook-relay` listens on loopback 8090 and forwards only POST `/api/webhooks/paypal` to `WEBHOOK_UPSTREAM` (default 8080). It rejects every other path/method and strips cookie/authorization headers. Point an explicitly authorized temporary HTTPS tunnel at that relay, never the full API. Remove the registration with `cmd/paypal-webhooks -mode delete -webhook <id>` and stop the tunnel/relay after testing. `-mode resend -event <actual-app-event-id> -webhook <id>` supports real historical delivery when provider inventory contains such events; it does not manufacture a new payment.

Set `SEED_PASSWORD` privately, then use `scripts/payments-smoke.ps1 -Action Prepare` once. It creates one synthetic $1 order and saves the intent identity before provider dispatch. The user approves that existing order through the local PayPal button. Once HELD, run `-Action Void -IntentID <id>` to verify the application's cancellation path. Use `-Action Read -IntentID <id>` to refresh sanitized observations. The script refuses to prepare another order over existing evidence. It has no capture action.
